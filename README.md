# **РУСИДО Tools — концепция программного комплекса**

**РУСИДО Tools** — набор Python-инструментов для работы с искусственным языком Русидо. Он должен решать две основные задачи:

1. **Русский → Русидо:** автоматически переводить обычный русский текст в соответствии с грамматикой Русидо.
2. **Валидатор Русидо:** проверять, соответствует ли текст алфавиту, лексике, морфологии и синтаксису языка, находить ошибки и предлагать исправления.

Дополнительно комплекс должен включать обратный анализатор Русидо, морфологический генератор, словарь, API для сторонних программ и консольный интерфейс.

Я бы проектировал его не как набор отдельных скриптов, а как небольшой лингвистический движок с общей грамматикой.

## **1. Архитектурная концепция**

**Общая схема**

**Входной текст**

Русский или Русидо

**Переводчик**

Русский → Русидо

**Валидатор**

Проверка Русидо

**Общее лингвистическое ядро**

Токенизатор · Лексикон · Морфология · Грамматика · Парсер

**spaCy**

Синтаксис и контекст

**pymorphy3**

Морфология русского

**NLTK**

Корпуса и статистика

**Результат**

Текст · AST · Диагностика · JSON · Отчёт

Ключевое архитектурное решение: **переводчик и валидатор должны использовать одну и ту же формальную грамматику Русидо**.

Например, если в грамматике существительное образуется по схеме:

```
ОСНОВА + ЧИСЛО + ПАДЕЖ
```

то генератор обязан создавать формы по этой схеме, а валидатор — распознавать их по той же схеме. Иначе со временем переводчик начнёт создавать формы, которые собственный валидатор будет считать ошибочными.

### **2.1. pymorphy3**

Основной инструмент для анализа исходного русского текста.

Он позволяет получать несколько вариантов разбора одного слова, его нормальную форму и грамматические признаки. Например, слово `стали` может быть существительным или глаголом, поэтому нельзя просто брать первый вариант разбора без учёта контекста.&#x20;

Основные задачи:

- определение начальной формы;
- определение части речи;
- определение рода, числа и падежа;
- определение времени, вида, лица и залога глагола;
- получение вариантов морфологического разбора.

### **2.2. spaCy**

Используется для контекстного анализа.

Рекомендуемый исходный компонент — русскоязычная модель `ru_core_news_sm`. Она предоставляет морфологический анализ, синтаксический парсер и лемматизацию. В её конфигурации также используется pymorphy3 для лемматизатора.&#x20;

Задачи:

- разделение текста на предложения;
- определение границ слов;
- определение синтаксических связей;
- поиск подлежащего, сказуемого и дополнения;
- определение связей между прилагательными и существительными;

### **2.3. NLTK**

NLTK не должен быть основой грамматического анализатора. Для этого у нас будет собственная грамматика.

Его лучше использовать для вспомогательных задач:

- обработка и подготовка корпусов;
- построение частотных словарей;
- анализ биграмм и триграмм;
- расчёт BLEU и других метрик сравнения переводов;
- исследование статистических закономерностей в текстах Русидо.

Для русской токенизации и морфологии предпочтительнее использовать spaCy и pymorphy3, а не полагаться на стандартный английский режим `word_tokenize` NLTK.&#x20;

## **3. Два основных компонента**

### **3.1. Транслятор&#x20;**`RusidoTranslator`

Задача — переводить русский текст на Русидо, сохраняя смысл исходного предложения и применяя правила искусственного языка.

Пример:

**Вход:**

```
Мой брат живёт в большом городе.
У него есть две собаки.
Вчера я прочитал интересную книгу.
Завтра мы будем работать вместе.
```

**Выход:**

```
мой брат жит в болший городе.
У нему ест два собаки.
Вчера я прочитал интересний книгу.
Завтра ми будеми работати вместе.
```

Это пример целевого поведения, а не окончательная таблица преобразований: точные основы некоторых слов и морфологические формы нужно закрепить в словаре Русидо.

#### **Этапы перевода**

1. **Нормализация**

   Очистка пробелов, Unicode-нормализация, сохранение пунктуации и исходного регистра.
2. **Токенизация**

   Разбиение текста на предложения, слова и знаки препинания.
3. **Морфологический анализ**

   Получение лемм и грамматических признаков каждого слова через pymorphy3 и spaCy.
4. **Контекстный анализ**

   Построение синтаксических связей: субъект, объект, сказуемое, определения, обстоятельства.
5. **Лексическое преобразование**

   Поиск соответствий в словаре Русидо: исходная русская лемма → основа Русидо.
6. **Грамматическое преобразование**

   Перенос числа, падежа, лица, времени, наклонения и других необходимых характеристик.
7. **Морфологическая генерация**

   Формирование слов по правилам Русидо.
8. **Синтаксическая сборка**

   Построение предложения с учётом SVO, предлогов, частиц и порядка слов.
9. **Проверка результата**

   Готовый текст передаётся собственному валидатору Русидо.

#### **Пример промежуточного анализа**

Исходное предложение:

```
Я читаю новую книгу.
```

Предполагаемый внутренний разбор:

```
{
  "sentence": {
    "type": "declarative",
    "order": "SVO",
    "subject": {
      "lemma": "я",
      "pos": "PRON",
      "person": 1,
      "number": "singular",
      "case": "nominative"
    },
    "predicate": {
      "lemma": "читать",
      "pos": "VERB",
      "tense": "present",
      "person": 1,
      "number": "singular"
    },
    "object": {
      "lemma": "книга",
      "pos": "NOUN",
      "number": "singular",
      "case": "accusative",
      "modifiers": [
        {
          "lemma": "новый",
          "pos": "ADJ"
        }
      ]
    }
  }
}
```

Целевая генерация:

```
Я читам новий книгу.
```

Здесь важно, что `новий` не получает падежного или числового окончания, а существительное получает винительный показатель `-у`.

#### **Обработка неоднозначностей**

Транслятор не должен безусловно выбирать первый вариант pymorphy3.

Например:

```
Я видел стали.
```

Слово `стали` может иметь несколько морфологических интерпретаций. Решение принимается по совокупности:

1. Вероятности разбора pymorphy3.
2. Контекстной информации spaCy.
3. Синтаксических связей.
4. Совместимости с лексиконом Русидо.

В текущем MVP (D-024) реализованы п. 1, 4 и часть п. 2 без spaCy: гипотеза
pymorphy3 выбирается по приоритету «лемма из лексикона → падеж по контексту
слева (предлог, SVO-объект, подлежащее) → частотная оценка». Пункт 3
(синтаксический парсер) остаётся в плане; валидатор не использует NLP (D-014).

При недостаточной уверенности транслятор должен:

- выбрать наиболее вероятный вариант;
- добавить предупреждение;
- при соответствующем режиме предоставить альтернативные переводы.

Предлагаемые режимы:

| Режим         | Поведение                                                             |
| ------------- | --------------------------------------------------------------------- |
| `strict`      | Не переводить неоднозначные конструкции без достаточной уверенности   |
| `normal`      | Выбирать наиболее вероятный вариант                                   |
| `best_effort` | Максимально стараться получить готовый текст, даже с предупреждениями |

### **3.2. Валидатор&#x20;**`RusidoValidator`

Валидатор должен определять, является ли входной текст корректным Русидо.

Важно разделять три понятия:

- **Лексическая корректность:** слово существует в словаре Русидо.
- **Морфологическая корректность:** слово построено по допустимым правилам.
- **Синтаксическая корректность:** слова образуют грамматически допустимую конструкцию.

Пример:

```
Я читам книгу.
```

Корректно

```
Я читаш книгу.
```

Ошибка

Причина: `читаш` — форма второго лица, а субъект `я` требует первого лица единственного числа.

```
Я книгиу читам.
```

Предупреждение

Все слова могут быть морфологически корректными, но порядок SVO нарушен. Поскольку спецификация допускает перестановки для выделения, это не обязательно ошибка.

#### **Уровни проверки**

| Уровень            | Проверки                                      |
| ------------------ | --------------------------------------------- |
| L1 — Lexical       | Алфавит, неизвестные слова, запрещённые буквы |
| L2 — Morphological | Основа, число, падеж, время, лицо, суффиксы   |
| L3 — Syntactic     | Порядок слов, связи, согласование глагола     |
| L4 — Semantic      | Противоречия и семантическая совместимость    |

Последний уровень необязателен для первой версии: полноценная семантическая проверка значительно сложнее грамматической.

#### **Пример диагностики**

Вход:

```
Я читаш новий книги.
```

Результат:

```
example.rusido:1:3: error R001
Глагол "читаш" не согласуется с субъектом "я".

  Я читаш новий книги.
    ^^^^^^

Ожидаемая форма: читам
Причина: первое лицо, единственное число.
```

Второй пример:

```
Я читаю новий книги.
```

Диагностика может обнаружить, что `читаю` не соответствует модели глагольной парадигмы Русидо, а `книги` имеет форму именительного множественного числа вместо требуемой формы винительного единственного числа.

Валидатор должен возвращать не только булево значение, но и полный отчёт.

Рекомендуемая модель результата:

```
{
  "valid": false,
  "score": 0.67,
  "errors": [
    {
      "code": "R001",
      "severity": "error",
      "message": "Неверная форма глагола",
      "word": "читаш",
      "expected": ["читам"],
      "line": 1,
      "column": 3
    }
  ],
  "warnings": [],
  "statistics": {
    "sentences": 1,
    "tokens": 4,
    "known_words": 4,
    "unknown_words": 0
  }
}
```

`score` — дополнительная оценка качества, а не математическое доказательство корректности. Решение `valid` принимается по формальным правилам.

## **4. Формализация грамматики для программы**

Это наиболее важная часть проекта. Грамматика должна храниться отдельно от программного кода, чтобы изменение Русидо не требовало переписывания движка.

### **4.1. Морфология существительного**

Формула:

```
ROOT + NUMBER + CASE
```

Правила:

```
noun:
  number:
    singular: ""
    plural: "и"

  case:
    nominative: ""
    accusative: "у"
    genitive: "о"
    dative: "е"

  order:
    - root
    - number
    - case
```

Генератор:

```
noun = "стол"# Singularстолстолустолостоле# Pluralстолистолиустолиостолие
```

Валидатор должен проверять форму именно по морфемной структуре, а не по простому набору окончаний.

Например, слово `столиу` должно разбираться как:

```
стол + и + у
ROOT  PL CASE
```

### **4.2. Морфология глагола**

```
verb:
  infinitive: "ти"

  present:
    singular:
      "1": "м"
      "2": "ш"
      "3": "т"

    plural:
      "1": "ми"
      "2": "те"
      "3": "ни"

  past:
    singular: "л"
    plural: "ли"

  future:
    auxiliary: "быти"
    pattern: "finite_auxiliary + infinitive"

  conditional:
    particle: "би"
    pattern: "particle + past"

  negation:
    particle: "не"
```

Важно: для основ на согласный требуется предусмотренная спецификацией соединительная гласная `е`.

Например:

```
чита- + м = читам
ид- + е + м = идем
```

Генератор должен знать тип основы, а не просто дописывать окончание к произвольной строке.

### **4.3. Морфология прилагательного**

```
adjective:
  suffix: "ий"
  inflection: false
  position: "before_noun"
```

Примеры:

```
новий
красивий
интересний
болший
```

Прилагательное не меняется в зависимости от падежа и числа существительного.

### **4.4. Отдельная таблица предлогов**

```
prepositions:
  в:
    static: dative
    direction: accusative

  на:
    static: dative
    direction: accusative

  к:
    case: dative

  из:
    case: genitive

  от:
    case: genitive

  без:
    case: genitive

  для:
    case: genitive

  о:
    case: dative
```

Для каждого предлога нужно хранить семантические условия, поскольку один русский предлог может требовать разных падежей Русидо.

### **4.5. Лексикон Русидо**

Это отдельный компонент, а не просто словарь русских слов.

Он должен содержать:

- русскую лемму;
- основу Русидо;
- часть речи;
- тип склонения или спряжения;
- допустимые варианты;
- признаки одушевлённости, если они нужны;
- синонимы и омонимы;
- исключения лексического уровня.

Пример:

```
{
  "lemma": "книга",
  "rusido_stem": "книг",
  "pos": "NOUN",
  "declension": "regular",
  "animacy": "inanimate",
  "translation": "книга",
  "source": "ru"
}
```

Пример глагола:

```
{
  "lemma": "читать",
  "rusido_stem": "чита",
  "rusido_infinitive": "читати",
  "pos": "VERB",
  "conjugation": "vowel_stem",
  "translation": "читать"
}
```

Пример прилагательного:

```
{
  "lemma": "новый",
  "rusido_stem": "нов",
  "rusido_form": "новий",
  "pos": "ADJ"
}
```

**Почему это важно:** нельзя надежно получать все основы Русидо простым удалением русских окончаний. Например, `книга → книг`, `дверь → двер`, `армия → арми`. Поэтому лексикон должен хранить именно целевую основу, независимо от того, как она получена.

### **4.6. База данных SQLite**

Лексикон и все переводческие данные должны храниться не только в статических JSON-файлах, но и в базе **SQLite** (`data/rusido.db`). SQLite выбрана сознательно: один файл, нулевая установка, транзакции, полнотекстовый поиск — достаточно и для словаря, и для корпуса, и для обучения.

База решает три задачи:

1. **Единый словарь.** Все слова Русидо (лемма, основа, часть речи, тип склонения/спряжения, алломорфы, перевод, частотность) хранятся в одном месте и редактируются через `rusido dictionary`, а JSON-файлы из `data/lexicon/` становятся формой импорта/экспорта.
2. **Корпус параллельных текстов.** Пары «русское предложение → русидское предложение» накапливаются в базе и становятся тестовым корпусом (README §11.5): валидация, поиск конструкций, статистика.
3. **Обучение переводчика.** Таблицы пар слов и пар предложений — обучающие данные для будущей статистической/нейросетевой модели перевода (вместо чисто правилового подхода).

Предлагаемая схема:

```sql
-- Словарь: все слова и переводы
CREATE TABLE words (
    id INTEGER PRIMARY KEY,
    lemma_ru TEXT NOT NULL,        -- русская лемма
    lemma_rusido TEXT NOT NULL,    -- лемма Русидо
    stem TEXT NOT NULL,            -- основа Русидо
    pos TEXT NOT NULL,             -- noun | verb | adj | pron | ...
    stem_type TEXT,                -- vowel | palatal | cons_stem ...
    allomorphs TEXT,               -- JSON: алломорфы основы
    frequency INTEGER DEFAULT 0,   -- частотность из корпуса
    grammar_version TEXT DEFAULT '1.0'
);

CREATE TABLE translations (
    id INTEGER PRIMARY KEY,
    word_id INTEGER NOT NULL REFERENCES words(id),
    source_form TEXT NOT NULL,     -- исходная форма (рус.)
    target_form TEXT NOT NULL,     -- форма Русидо
    context TEXT                   -- пример употребления
);

-- Параллельный корпус
CREATE TABLE corpus_sentences (
    id INTEGER PRIMARY KEY,
    source_ru TEXT NOT NULL,       -- русское предложение
    target_rusido TEXT NOT NULL,   -- перевод Русидо
    valid INTEGER,                 -- результат валидации
    source TEXT                    -- origin файла / ручной ввод
);

-- Индексы для поиска и обучения
CREATE INDEX idx_words_lemma ON words(lemma_ru);
CREATE INDEX idx_translations_pair ON translations(source_form, target_form);
```

Интеграция с кодом: `Lexicon` получает второй бэкенд хранения (`LexiconStorage`: JSON или SQLite) с одинаковым интерфейсом, так что переводчик и валидатор не меняются. CLI из §8.5 работает с базой:

```
rusido dictionary add --lemma "читать" --stem "чита" --pos verb --infinitive "читати"
rusido dictionary lookup "читать"
rusido dictionary export dictionary.json
rusido corpus add --ru "Я читаю книгу." --rusido "Я читам книгу."
rusido corpus stats
```

При разработке важно: база создаётся и мигрирует автоматически при первом запуске; валидатор и морфологический движок по-прежнему должны работать без неё (только на JSON-лексиконе), чтобы проверка текстов Русидо не зависела от SQLite.

## **7. Python API**

Публичный API должен быть простым. Пользователю не нужно знать внутреннее устройство spaCy, pymorphy3 или AST.

### **7.1. Инициализация**

```
from rusido import (    RusidoTranslator,    RusidoValidator,    RusidoConfig,)config = RusidoConfig(    grammar_version="1.0",    analysis_backend="spacy",    strict=False,)translator = RusidoTranslator(config)validator = RusidoValidator(config)
```

### **7.2. Перевод**

```
result = translator.translate(    "Я читаю новую книгу.")print(result.text)print(result.warnings)
```

Результат:

```
Я читам новий книгу.
```

Пример структуры `TranslationResult`:

```
@dataclassclass TranslationResult:    source: str    text: str    warnings: list    alternatives: list    confidence: float    grammar_version: str
```

### **7.3. Валидация**

```
report = validator.validate(    "Я читам книгу.")print(report.valid)print(report.errors)print(report.warnings)
```

Дополнительно:

```
if report.valid:    print("Корректный текст Русидо")else:    print("Найдены ошибки")for error in report.errors:    print(error.message)    print(error.suggestion)
```

### **7.4. Морфологический анализ**

Это отдельная публичная возможность, полезная для обучения языку и отладки.

```
from rusido import RusidoAnalyzeranalyzer = RusidoAnalyzer()result = analyzer.analyze("столиу")for item in result:    print(item.root)    print(item.number)    print(item.case)
```

Ожидаемая интерпретация:

```
root: стол
number: plural
case: accusative
```

### **7.5. Словарь**

```
from rusido import Lexiconlexicon = Lexicon()entry = lexicon.lookup("читать")print(entry.rusido_stem)print(entry.rusido_infinitive)
```

Ожидаемый вывод:

```
чита
читати
```

### **7.6. Пакетный перевод**

```
texts = [    "Я читаю книгу.",    "Он работает в городе.",    "Мы изучаем русский язык."]results = translator.translate_batch(texts)for result in results:    print(result.text)
```

Желательно, чтобы пакетный перевод переиспользовал одну загруженную модель spaCy и один экземпляр pymorphy3, а не создавал их для каждого предложения.

### **8.2. Перевод текста**

### **8.5. Работа со словарём**

```
rusido dictionary list                         # первые 50 записей
rusido dictionary list -p verb -a              # глаголы с алломорфами
rusido dictionary list -s книг -n 0            # поиск по лемме/основе/переводу
rusido dictionary list --format md -o lex.md   # список в Markdown
rusido dictionary export lex.json              # экспорт в JSON (по умолчанию)
rusido dictionary export --format md -o lex.md # экспорт в Markdown
rusido dictionary import                       # импорт в SQLite
```

`dictionary list` понимает `-p/--pos` (можно повторять), `-a/--allomorphs`,
`-s/--search`, `-n/--limit` (`0` — все), `--format {text,md,json}` и `-o/--output`.
По умолчанию читается встроенный лексикон; `--source db --db path.db` берёт
записи из SQLite. Команды `word`, `lookup`, `search`, `add` из раннего плана
пока не реализованы — их заменяет `dictionary list` с фильтрами.

Последняя команда `dictionary add` должна открывать интерактивный режим добавления слова или принимать параметры, например:

```
rusido dictionary add \
  --lemma "читать" \
  --stem "чита" \
  --pos verb \
  --infinitive "читати"
```


Таким образом, утилиту можно будет использовать как интерактивный инструмент, как проверяющий этап в CI/CD и как компонент других программ.

### **8.7. Корпус и статистика**

Команды работают с SQLite-базой из §4.6:

```
rusido corpus add --ru "Я читаю книгу." --rusido "Я читам книгу."
rusido corpus import parallel_pairs.tsv
rusido corpus search "читам"
rusido corpus stats              # число пар, покрытие лексикона, доля валидных
rusido stats                     # частотность слов по корпусу
```

Накопленные пары предложений — основа тестового корпуса (§11.5) и обучающих данных для статистического переводчика будущих версий.

## **9. Коды ошибок**

Рекомендую сразу создать единую систему диагностических кодов.

| Код  | Категория   | Описание                                    |
| ---- | ----------- | ------------------------------------------- |
| R001 | Syntax      | Неверное согласование глагола с субъектом   |
| R002 | Morphology  | Неверный падеж                              |
| R003 | Morphology  | Неверное число                              |
| R004 | Morphology  | Неверная форма глагола                      |
| R005 | Lexicon     | Неизвестное слово                           |
| R006 | Orthography | Запрещённая буква                           |
| R007 | Orthography | Удвоенная согласная (некорректное написание)|
| R008 | Syntax      | Некорректная именная группа                 |
| R009 | Syntax      | Некорректная глагольная конструкция         |
| R010 | Syntax      | Нарушение обязательного порядка             |
| R011 | Lexicon     | Неверная лексическая основа                 |
| R012 | Morphology  | Неправильный порядок морфем                 |
| R013 | Syntax      | Некорректная конструкция с предлогом        |
| R014 | Morphology  | Неизвестная форма словоизменения            |
| R015 | Numerals    | Нарушение правила числа после числительного |
| R016 | Grammar     | Неизвестная грамматическая конструкция      |
| R017 | Orthography | Отсутствует финальная пунктуация            |
| R018 | Orthography | Символ вне алфавита                         |

Формальная спецификация каждого кода — в `rusido.validation.codes.CODES`:
категория, уровень проверки, точное условие выдачи и статус (`implemented` /
`reserved`). Коды R002—R004, R009—R014 и R016 зарезервированы: их смысл
зафиксирован, но проверки пока не выдаются. R007 закреплён за удвоенными
согласными; символы вне алфавита выдаются отдельным кодом R018, а отсутствие финальной
пунктуации — R017.

Каждая диагностика должна содержать:

```
@dataclassclass Diagnostic:    code: str    severity: str    message: str    suggestion: str | None    line: int    column: int    start: int    end: int
```

Уровни:

- `error` — нарушение обязательного правила;
- `warning` — подозрительная конструкция;
- `info` — информационное сообщение.

Принципиально важно, чтобы ошибки не были просто текстовыми сообщениями, а имели стабильные коды. Это позволит сторонним редакторам, IDE и другим программам обрабатывать их автоматически.

`RusidoConfig` должен позволять выбирать версию грамматики, режим проверки, путь к словарю и используемый NLP-бэкенд.

Это даст возможность развивать Русидо, не ломая предыдущие версии.

Например:

```
rusido validate text.rus --grammar 1.0
rusido translate text.txt --grammar 1.1
```

Версионирование необходимо не только самому языку, но и словарю: форма, которая корректна в одной версии, необязательно останется корректной после изменения правил.

## **11. Система тестирования**

Поскольку Русидо — формализованный язык, тестирование должно быть не только функциональным, но и грамматическим.

### **11.1. Unit-тесты морфологии**

```
def test_noun_singular_nominative():    assert inflect_noun("стол", "singular", "nominative") == "стол"def test_noun_plural_accusative():    assert inflect_noun("стол", "plural", "accusative") == "столиу"def test_verb_present_first_person():    assert conjugate_verb("читати", 1, "singular") == "читам"
```

### **11.2. Тесты валидатора**

```
def test_valid_sentence():    assert validator.validate("Я читам книгу.").validdef test_invalid_verb():    assert not validator.validate("Я читаш книгу.").validdef test_valid_plural():    assert validator.validate("У нему ест два собаки.").valid
```

### **11.3. Тесты целостности грамматики**

Очень важный тип тестирования:

```
def test_translator_output_is_valid():    result = translator.translate(        "Я читаю новую книгу."    )    report = validator.validate(result.text)    assert report.valid
```

Это гарантирует, что транслятор не создаёт заведомо некорректные конструкции.

Ещё лучше сделать массовые тесты:

```
def test_all_generated_noun_forms():    for noun in lexicon.get_all_nouns():        for number in ["singular", "plural"]:            for case in [                "nominative",                "accusative",                "genitive",                "dative"            ]:                form = morphology.generate_noun(                    noun,                    number,                    case                )                assert validator.validate_word(form).valid
```

### **11.4. Интеграционные тесты**

Отдельный набор должен проверять:

- перевод целых абзацев;
- перевод сложных предложений;
- обработку числительных;
- обработку местоимений;
- обработку отрицаний;
- обработку пассивного залога;
- неизвестные слова;
- имена собственные;
- пунктуацию;
- сохранение структуры абзацев.

### **11.5. Корпус Русидо**

Предлагаю со временем собрать собственный тестовый корпус:

```
corpus/
├── basic/
│   ├── nouns.txt
│   ├── verbs.txt
│   └── adjectives.txt
│
├── sentences/
│   ├── simple.txt
│   ├── complex.txt
│   ├── questions.txt
│   └── negative.txt
│
├── paragraphs/
│   ├── everyday.txt
│   ├── scientific.txt
│   └── fiction.txt
│
└── invalid/
    ├── orthography.txt
    ├── morphology.txt

```

В перспективе этот корпус позволит не только проверять грамматику, но и оценивать качество перевода на реальных текстах. Хранилищем корпуса служит SQLite-база (§4.6): файлы в `corpus/` — форма импорта, база — рабочее состояние, на основе которого считается статистика и готовятся обучающие выборки.

## **13. Проблемы исходной спецификации, которые нужно решить до разработки**

Здесь я бы не стал сразу переносить все правила Русидо в программный код. В самой концепции есть несколько неоднозначностей, которые повлияют на архитектуру.

| Проблема                 | Что нужно решить                                                       |
| ------------------------ | ---------------------------------------------------------------------- |
| Будущее время            | Формально определить парадигму вспомогательного `будти`                |
| Местоимения              | Определить статус `она` и `оно` в бесполой системе                     |
| Повелительное наклонение | Устранить противоречие между `читай`, `пиши`, `иди`                    |
| Основа существительных   | Формализовать извлечение и хранение основ                              |
| Прилагательные           | Уточнить правила получения основы и добавления `-ий`                   |
| Буква `ь`                | Описать правила её использования в конце и внутри основы               |
| Числительные             | Закрепить обработку чисел и составных числительных                     |
| Вид глагола              | Определить, как передавать различие совершенного и несовершенного вида |
| Имена собственные        | Определить политику сохранения и транслитерации имён                   |
| Пассив                   | Уточнить положение `се` и границы конструкции                          |
| Творительный падеж       | Определить, как передавать русский творительный при четырёх падежах    |

Особенно важны четыре момента.

**1. Будущее время.**

В спецификации написано `будти + инфинитив`, но примеры используют `будем`, `будени` и другие личные формы. Я предлагаю закрепить отдельную парадигму вспомогательного глагола:

```
я будем читати
ти будеш читати
он будет читати
ми будеми читати
ви будете читати
они будени читати
```

Это согласуется с общей системой окончаний настоящего времени при основе `буд-`.

**2. Повелительное наклонение.**

Текущие примеры `писати → пиши` и `читати → читай` не следуют одному очевидному правилу. Нужно либо определить регулярное чередование основ, либо хранить отдельные основы повелительного наклонения. Для языка, цель которого — устранение исключений, предпочтительно первое, если оно действительно покрывает все глаголы.

**3. Местоимения.**

Таблица личных местоимений содержит `он`, но примеры предполагают возможность перевода и женского русского местоимения. Нужно определить, будет ли `он` универсальным местоимением третьего лица единственного числа или в Русидо сохранятся отдельные лексические формы `он` и `она`.

**4. Основы слов.**

Валидатор не должен угадывать основу только по окончаниям. Сочетание `ROOT + NUMBER + CASE` должно проверяться с учётом словарной записи и морфемной сегментации.

Все решения лучше хранить в `docs/grammar.md` и `docs/decisions.md`, а затем фиксировать номер версии грамматики.

## **17. Итоговая концепция**

Я бы позиционировал проект следующим образом:

**Rusido Tools — модульная NLP-платформа для регуляризированного русского искусственного языка.**

В ней будут три главных направления:

**Rusido Core**

Фундамент

Морфология, грамматика, лексикон, токенизация, AST и парсер.

**Rusido Translator**

Русский → Русидо, морфологический перенос, синтаксическая трансформация и генерация.

**Rusido Validator**

Проверка орфографии, лексики, словоизменения и синтаксиса Русидо.

**Моя главная рекомендация по архитектуре:** не начинать разработку непосредственно с интеграции spaCy и перевода предложений. Сначала следует реализовать формальный морфологический движок Русидо, словарь и валидатор. Когда они будут работать независимо от русского NLP, транслятор станет намного проще: ему останется преобразовывать русский синтаксический разбор в промежуточную структуру и передавать её генератору Русидо.

Так получится не просто переводчик, а программная реализация грамматики языка, которую впоследствии можно будет использовать в редакторе, словаре, обучающих приложениях и даже в собственных NLP-экспериментах.

Полезный следующий шаг — реализовать **Rusido Core 0.1**: морфологический движок, словарь, генератор словоформ и первые unit-тесты.
