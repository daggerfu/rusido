# User Stories — РУСИДО Tools

Дата: 2026-11-17. Формат: «Как <актор>, я хочу <цель>, чтобы <ценность>».
Критерии приёмки ссылаются на тесты `tests/` и разделы документации.
Акторы: **Лингвист** (автор языка/спеки), **Пользователь** (пишет/читает Русидо),
**Разработчик** (интегрирует пакет), **Исследователь** (оценивает качество).

## Epic A. Перевод (переводчик)

- **US-A1.** Как Пользователь, я хочу перевести русский текст в Русидо через CLI
  (`rusido translate`), чтобы читать результат сразу.
  Приёмка: CLI §8 README; `test_cli.py`; «Я читаю книгу.» → «Я читам книгу.».
- **US-A2.** Как Пользователь, я хочу видеть предупреждения о неизвестных словах и
  confidence, чтобы понимать надёжность перевода.
  Приёмка: `TranslationResult.warnings/confidence`; `test_unknown_word_adds_warning`.
- **US-A3.** Как Пользователь, я хочу, чтобы перевод работал без установленного
  pymorphy3 (эвристики), чтобы пакет был переносим.
  Приёмка: `use_nlp=False`; `test_translator.py` (heuristic-фикстуры).
- **US-A4.** Как Разработчик, я хочу пакетный перевод (`translate_batch`) и
  программный API, чтобы встраивать переводчик в пайплайны.
  Приёмка: `RusidoTranslator.translate_batch`; README §7 (API).
- **US-A5.** Как Пользователь, я хочу, чтобы служебные слова §2.2 переводились
  словарно (что→што, чтобы→штоби…), чтобы не было «неизвестное слово».
  Приёмка: `RU_TO_LEMMA_OVERRIDES`; `test_service_word_overrides`.

## Epic B. Валидация (валидатор)

- **US-B1.** Как Пользователь, я хочу проверить текст Русидо с кодами ошибок R001—R018,
  чтобы находить ошибки по документированным правилам.
  Приёмка: `validation/codes.py` (реестр); README §9; `test_diagnostic_codes.py`.
- **US-B2.** Как Пользователь, я хочу видеть позицию ошибки (line/column/start/end)
  и исправление (suggestion), чтобы быстро её чинить.
  Приёмка: `Diagnostic`; `test_diagnostics_carry_positions`.
- **US-B3.** Как Лингвист, я хочу, чтобы все примеры Rusido.md проходили валидацию,
  чтобы спецификация и код не расходились.
  Приёмка: `test_spec_sample_text_validates` + аудит примеров (2026-11-17).
- **US-B4.** Как Пользователь, я хочу, чтобы цифры, латиница, аббревиатуры и оригинальные
  имена (§1.1, §2.9, §6.7) не считались ошибками, чтобы писать естественные тексты.
  Приёмка: `core/tokens.py`; `test_text_layers.py`.
- **US-B5.** Как Разработчик, я хочу строгий режим (финальная пунктуация R017) и коды
  выхода CLI, чтобы встраивать валидацию в pre-commit/CI.
  Приёмка: `strict`; `test_cli.py` (коды выхода).

## Epic C. Морфология и лексикон

- **US-C1.** Как Лингвист, я хочу морфемный разбор слова (`RusidoAnalyzer`), чтобы
  видеть корень/число/падеж/алломорфы.
  Приёмка: `test_analyzer.py`; Rusido.md §7.1.1.
- **US-C2.** Как Лингвист, я хочу задавать грамматику YAML-профилем (`grammar_version`),
  чтобы экспериментировать с параметрами языка без правки кода.
  Приёмка: `core/grammar.py`; `test_grammar_yaml.py`; `test_custom_grammar_version_changes_output`.
- **US-C3.** Как Пользователь, я хочу пополнять лексикон (`dictionary import`,
  `Lexicon.add`) и искать по корпусу (`corpus search`), чтобы развивать словарь.
  Приёмка: `test_storage.py`; `test_lexicon.py` (roundtrip JSON).
- **US-C4.** Как Лингвист, я хочу, чтобы основы пополняемых слов нормализовались
  автоматически (ё/ы/э/ъ, удвоенные), чтобы не писать формы руками.
  Приёмка: `Lexicon.add` нормализация; `test_lexicon.py`.

## Epic D. Качество и выход из MVP (цель v0.2)

- **US-D1.** Как Пользователь, я хочу контекстный выбор падежа при переводе
  («книги» им. мн. vs род. ед. по контексту предложения), чтобы не получать «книго»
  там, где имелось в виду «книги».
  Приёмка: новые тесты на пару минимальных контекстов; снятие пункта TODO (NLP).
- **US-D2.** Как Пользователь, я хочу перевод связки («будет») и местоимений
  «она/оно» → `он` по §5.1, чтобы спека и переводчик совпадали.
  Приёмка: решение в Rusido.md + D-xxx; тесты переводчика.
- **US-D3.** Как Разработчик, я хочу spaCy-бэкенд и режимы strict/normal/best_effort
  с порогами уверенности, чтобы переводить сложные предложения.
  Приёмка: `analysis_backend`; README §13; критерий выхода из MVP №4.
- **US-D4.** Как Пользователь, я хочу проверку управления предлогов и score-оценку
  текста, чтобы видеть не только ошибки, но и общее качество.
  Приёмка: R002/R003/R013 реализованы; `ValidationReport.score`.
- **US-D5.** Как Исследователь, я хочу параллельный корпус и BLEU-метрику, чтобы
  измерять прогресс качества перевода между версиями.
  Приёмка: модуль `evaluation/`; метрика зафиксирована в `02-to-be.md` §4.
- **US-D6.** Как Разработчик, я хочу CI (pytest на 3.11–3.13) и линтер/типизацию,
  чтобы регрессии ловились до релиза.
  Приёмка: GitHub Actions зелёный; ruff/mypy в вехе v1.0.

## Приоритеты (MoSCoW, веха v0.2)

- **Must:** US-D1, US-D2, US-D6, US-D4 (часть: R-коды/управление предлогов).
- **Should:** US-D3 (базовый spaCy-режим), ручная вычитка основ (US-C3 продолжение).
- **Could:** US-D5 (baseline BLEU), score-формулы, Rich-вывод.
- **Won't (v0.2):** PyPI, property-тесты, полный набор CLI-команд README §8.
